Getting started

SabotPress has three first-class ways to run. Pick the one that matches what you need rather than learning infrastructure for sport.

Browser / PWA

Open the browser edition, choose Start on this device, name the publication, choose modules, and enter the newsroom. No account is required for browser-local use. Work stays in that browser until you explicitly export or publish it.

Desktop

The desktop edition uses local SQLite plus local media storage. It is the better choice for large media libraries, AudioLab/PrintLab work, filesystem access, and long offline sessions.

Self-hosted web

Use this when several editors need to share one publication or when the public website should run on infrastructure you or a collective controls.

Reinstalling is not a factory reset. App files and publication data are separate. Updating SabotPress should not erase somebody's publication.

Publishing basics

  1. Create a post from New or Posts.
  2. Add images/audio from the editor or Media Library.
  3. Save drafts while you work.
  4. Preview the public site before publishing.
  5. Use Publish Online when a local publication is ready to move to a public host.

Modules control which tools appear. Turning a module off hides that workflow; it does not silently delete existing publication data.

$0 public hosting

A local SabotPress publication is not automatically a public website. To put it online for free, you need a compatible host with persistent database and media storage. The currently tested no-cost model is Cloudflare Pages/Workers-style hosting with D1/R2-compatible storage.

  1. Export a complete .sabotpress backup from Publish Online.
  2. Create a compatible SabotPress web deployment.
  3. Attach persistent database and media storage.
  4. Import the backup into that hosted instance.
  5. Use the host-provided address. A custom domain is optional.

SabotPress does not silently create hosting accounts, buy domains, or upload local publication data merely because you opened the publishing screen.

What to ask a community or collective host

A host does not need a special SabotPress account. They need to be willing to run the open web edition and provide:

  • persistent SQL-compatible database storage
  • persistent media/object storage
  • HTTPS
  • a stable public address
  • backups of both database and media
  • a safe application update path that does not replace publication data

Plain-language version: “Can you run this web app with persistent database and media storage, HTTPS, and backups?”

Server setup

The server edition is the advanced route. It needs the SabotPress web build, persistent database storage, persistent media storage, HTTPS, admin/session secrets, and the schema initialized.

  1. Deploy the web application.
  2. Attach database storage.
  3. Attach media storage.
  4. Configure admin/session secrets.
  5. Run schema setup.
  6. Verify Site Health.
  7. Import a .sabotpress backup if migrating from browser or desktop.

Provider-specific deployment details remain in repository documentation for maintainers, but ordinary desktop/browser use should not require GitHub.

Noblogs / WordPress migration

  1. Export the old WordPress/Noblogs site before it disappears.
  2. Keep the original export untouched somewhere safe.
  3. Keep a separate copy of uploads/media if possible.
  4. Create the SabotPress publication and enable the modules you need.
  5. Import posts and media.
  6. Check titles, dates, authors, categories/projects, links and featured images.
  7. Preview the archive and important pages.
  8. Only then connect a domain or redirect visitors.

Do not delete the old export after import. Keep it as the source archive until you are satisfied the migration is complete.

Backups

Desktop automatic backups

Automatic desktop backups are on by default. The default schedule is daily, keeping the most recent 7 backups. Each backup contains a safe SQLite copy plus the local media folder. In Backups you can switch automatic backups on/off, choose daily or weekly, keep 3/7/14/30 copies, run a backup immediately, and open the backup folder.

Local automatic backups are still on the same computer. They protect against accidental edits or a damaged local database, but not theft, disk failure, or loss of the whole machine.

Portable backup

Publish Online → Export complete backup creates a .sabotpress package for moving a publication between browser, desktop and server editions. Keep at least one portable backup somewhere outside the device running SabotPress.

Browser edition

Browsers do not allow a web app to silently write backup files into arbitrary folders in the background. SabotPress therefore reminds browser-local users to export a portable backup. Browser storage persistence helps, but clearing site data can still remove local work.

Server edition

A server host should schedule infrastructure backups for both database and media. SabotPress also provides a manual verified server snapshot, but the app cannot truthfully promise a server backup schedule unless the host has configured one.

Where your work lives

Desktop

The SQLite database, media, backup settings, and automatic backup folder live in the operating system's SabotPress application-data directory. Reinstalling or upgrading the app normally leaves this directory alone.

Browser

Browser-local SabotPress uses IndexedDB for publication records and media. It normally survives reloads and browser restarts in the same profile, but clearing site data or resetting that profile can remove it.

Server

Server installations use the configured persistent database and media storage. The host is responsible for making those stores durable and backing them up.
