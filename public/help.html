Getting started

SabotPress has three normal ways to run. Pick the one that matches what you need instead of learning infrastructure for sport.

Browser / PWA

Open the browser edition, start a publication with no account, and keep the work on that device. Export regular portable backups because clearing browser site data can remove local work.

Desktop

The desktop edition keeps its SQLite database and uploaded media in the operating system's SabotPress application-data folder. Reinstalling or upgrading the app normally leaves that folder alone, so your publication survives an update.

Self-hosted web

Use this for a shared multi-user publication or when you want the public site and storage on infrastructure you control.

Reinstalling is not a factory reset. That is intentional. An update should not delete a publication. If you are testing a truly fresh install, remove the SabotPress application-data folder separately after exporting anything you want to keep.

$0 public hosting

The currently tested no-cost route is a Pages/Functions style host with persistent database and media storage. SabotPress currently supports the Cloudflare Pages/Workers model with D1/R2-compatible storage. Free tiers can change.

  1. Export a complete .sabotpress backup from Publish Online.
  2. Create a SabotPress web deployment on the host.
  3. Import the backup into that deployment.
  4. Use the host-provided address. A custom domain is optional.

SabotPress does not silently create hosting accounts, buy domains, or upload local publication data merely because you opened the publishing screen.

What to ask a community or collective host

A host does not need a special SabotPress company account. They need to be willing to run the open web edition and provide:

  • persistent database storage
  • persistent media/object storage
  • HTTPS
  • a stable public address
  • backups of both database and media
  • a way to update the SabotPress application without replacing publication data

Useful question: “Can you run a Node/edge-style web app with persistent SQL-compatible data and persistent media storage, and back both up?”

Server install guide

The server edition is the advanced route. It is appropriate when you or a host actually want to operate the infrastructure.

  1. Deploy the SabotPress web application.
  2. Attach the required persistent database binding.
  3. Attach persistent media storage.
  4. Set the admin/session secrets required by the deployment adapter.
  5. Run the database schema setup.
  6. Verify Site Health before publishing.
  7. Import an existing .sabotpress backup if migrating from browser or desktop.

Provider-specific details can vary. The repository documentation remains the maintainer reference for unusual server setups, but ordinary users should not need it for browser or desktop use.

Noblogs / WordPress migration

The goal is to move the publication, not recreate every WordPress implementation detail.

  1. Export your old WordPress/Noblogs content before the old site disappears.
  2. Keep a separate copy of uploads/media.
  3. Start a SabotPress publication and choose the modules you actually need.
  4. Import posts and media using the available import tools.
  5. Check titles, dates, authors, categories/projects, links and featured images.
  6. Preview the archive before making the new site public.
  7. Only then connect a domain or redirect traffic.

Keep the original export. Migration is much less frightening when the source archive remains untouched somewhere you control.

Backups

Portable backup: Publish Online can export a complete .sabotpress package for moving between browser, desktop and server editions. This is the most useful user-controlled backup.

Server snapshot: the Backups admin screen exports a verified server-data snapshot. It is currently a manual action, not a scheduled backup service.

Browser edition: SabotPress reminds you when meaningful local content exists and no recent portable backup has been recorded.

There is currently no configurable automatic backup schedule in SabotPress. A host may run its own scheduled infrastructure backups. Desktop and browser users should use portable exports until an automatic local snapshot scheduler is added.
